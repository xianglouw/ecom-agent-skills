# 潦草手写加固手册

手写单最怕的不是「认不出」，是**认错了还看不出来**：表格填得满满当当，数字却有一半是模型脑补的，当天账就对不上。

这份手册解决一件事：**字迹潦草、涂改、简写混排的单据，怎么让识别结果可信，或者干脆承认「这行读不准」并告诉你去补拍哪一格。**

配套：拍照规范与提示词见 [ocr-playbook.md](ocr-playbook.md)；字段写进表格的规矩见 [field-schema.md](field-schema.md)。

## 一、潦草字迹是怎么把表格做错的

四种失效模式，比「看不清」三个字具体得多，也各自有对应解法：

| 失效模式 | 现场长什么样 | 后果 |
|---|---|---|
| **脑补** | 数字连笔（3/8、5/6、0/6），模型挑了一个「更常见」的值填上 | 表格完整但数字是错的，对账时才发现 |
| **串行** | 行高不齐、字压在格线上，第 5 行的数量被算到第 4 行 | 单行看都合理，合计却对不上 |
| **漏行 / 多行** | 划掉的行、圈号分组（②③）、空白跳号被当成空行或备注丢掉 | 少记一笔，或把合计行也录成一条明细 |
| **列错位** | 单价列整列空着、金额列只填个别行，模型把金额塞进单价 | 数量×单价 与单据金额「自动对不上」，其实是列错了 |

## 二、四遍读法（P0–P4）

**关键：不要一遍读完全部信息。** 一次既认版面又抠数字，模型会在最潦草的地方开始编。分四遍，每遍只干一件事。

| 遍次 | 只做什么 | 产出 | 停下来问自己 |
|---|---|---|---|
| **P0 全景** | 只看骨架：几张单、每张几行、行号起止、单据号、日期、采购还是销售、有没有圈号分组 | 单据清单 + 行数 | 一共几行？有没有跳号、划掉的行？ |
| **P1 行级** | 按行裁切、放大 2–4 倍逐行读，每行只抠四个格：品名 / 数量 / 单价 / 金额 | 每行的原始读数 | 这个数字是「看清的」还是「猜的」？ |
| **P2 交叉** | 换一种读法再来一遍（第一遍按行读，第二遍按列读；或换一个模型/换一次提问），两次结果逐字段比对 | 一致字段 + 不一致字段 | 哪几个格子两遍读出来不一样？ |
| **P3 校准** | 用简写映射表和历史价格库校验；落在合理区间的提高把握，偏离的标「疑似识别错位」 | 可信字段 / 存疑字段 | 数字对不上是识别错了，还是行情变了？ |
| **P4 未决** | 仍然读不准的，生成补拍指令，**不填数** | 补拍清单 | 这一格要拍哪儿才能看清？ |

**P2 是分水岭。** 只读一遍就输出的结果，潦草场景下不该直接进账；两遍读出来一致的字段，才配得上高置信度。

## 三、置信度按字段给，不按行给

一行的分数取**关键字段的最低分**，不取平均——品名 0.95、单价 0.5 的行，整行就是 0.5。

| 字段状态 | 打分 | 后续 |
|---|---|---|
| 印刷体，或清晰手写、逐位可辨 | 0.95–1.0 | 直接入账 |
| 手写清楚，个别字靠上下文确认 | 0.80–0.95 | 入账，抽样复核 |
| 有连笔/涂改/淡笔迹，或简写没见过 | 0.60–0.80 | 入账但进「异常行」，对照原图复核 |
| 有一位数字靠猜，或给了候选值 | < 0.60 | **不进日结**，进隔离清单与补拍清单 |

脚本默认线：`--low-confidence 0.75`（告警，进异常行）与 `--confidence-floor 0.6`（低于此线直接隔离，不进日结）。两条线都可以按自家单据质量调，但**不要把 floor 调到 0.6 以下**——那就是允许猜。

## 四、候选值：宁可给三个，不要猜一个

读不准时不要硬选一个，把可能的写法都交出来，人工一眼就能定：

```json
{"item_raw": "1190 17P 触摸", "candidates": ["1190 17P 触摸", "1290 17P 触摸"], "confidence": 0.55}
```

| 规矩 | 说明 |
|---|---|
| 候选 ≤ 3 个，按可能性排序 | 凑数式候选等于没给 |
| 给了候选，confidence 必须 ≤ 0.6 | 脚本据此把该行挡在日结之外 |
| 数字类字段给候选要说清差在哪一位 | 写「3 或 8（首位）」比写「可能是 3」有用 |
| 候选值进「候选值」列（`candidates`） | 脚本读到非空即标「字段有多个候选」，进补拍清单 |

**有候选 = 没读准 = 不入账。** 这一条比对账快得多：错一笔进账，闭店后要翻半天。

## 五、分组标记、涂改与符号怎么读

手写单上一半的符号不是数据，是记号。读错了比读不出更麻烦：

| 记号 | 通常含义 | 正确读法 | 错误读法 |
|---|---|---|---|
| 圈号 `②` `③` | 分组编号或第几笔 | 记进 note（如「第 5–9 行共用圈号 ②」），不当作数量 | 当成数量填进 qty 列 |
| 打勾 `√` | 已核对 / 已付款 | 记进 note | 当成删除线，把行丢掉 |
| 画叉 `×` | 已发货 / 已作废（**两种都可能**） | 拿不准时把该行标「疑似作废行」交人工确认 | 直接删行，或少记一笔 |
| 斜线划改 | 划掉的是错字，旁边是新值 | 用新值，旧值写进 note | 取两个值的平均或取先写的 |
| 行号跳号（1,2,3,5） | 第 4 行被划掉或被跳过 | 在 note 里点名，**不自动补行** | 按行号补一行空数据 |
| 空白合计栏 | 单据没写合计 | 按 数量×单价 补齐并标注 | 用合计倒推单价 |

## 六、价格库：把「看不清」变成「对得上 / 对不上」

准备一份 `价格库.csv`（`品名或简写,参考单价,下限,上限,币种`），取自往期台账或供应商报价，用 `--price-ref` 传进来。脚本对每一行给出三种结果之一：

| 核对结果 | 判定 | 处理 |
|---|---|---|
| 命中区间 | 单价落在下限与上限之间 | 把握度上调，正常入账 |
| 偏离区间 | 超出上下限，或与参考价偏差超过 `--price-tolerance`（默认 30%） | 标「疑似识别错位」，**回看原图**，不改数 |
| 库里没有 | 品名未收录 | 保持原样，进待确认清单 |

**价格库只用来「怀疑」，不用来「改写」。** 偏离不等于单子错，也可能是行情变了——脚本只标出来，改不改由人定。

顺带会检出两类高频错位（同样只标不改）：

- **数量与单价写反**：单价填了很小的数（≤ 10）而数量填了大数（≥ 100），多半是两列抄反了；
- **单价列抄成金额**：单据金额与单价是同一个数，而数量大于 1。

## 七、补拍指令怎么写

读不准的格子，**补拍永远比逐格纠错快**。补拍清单按「照片 → 行 → 格子 → 怎么拍」组织：

表格里**一行就是一个待办**（不把同一张照片的多行挤进一个格子），拿到手机可以逐条对着拍、逐条划掉；
同一张照片未决行超过 5 行时，「建议动作」会改写成「整张重拍」——逐行特写反而更慢。

```text
照片 IMG_0902_采购单.jpg
- 第 5 行「单价」：3 与 8 连笔，靠近该格单独拍一张，或斜 45° 侧拍让光扫过笔痕
- 第 7 行「数量」：数字压在格线上，整行特写一张
- 合计栏：整张单据没写合计，确认是否漏拍单据下半部分
```

| 原则 | 说明 |
|---|---|
| 一次补拍解决所有未决项 | 别让店员来回跑三趟 |
| 需要特写的行 ≤ 5 行 | 超过 5 行，整张重拍更快 |
| 指明「哪张照片、哪一行、哪个格子」 | 「拍清楚点」这种指令等于没说 |
| 补拍前先看是不是拍照问题 | 连续多行低置信，先修拍照姿势，别逐行抠 |

## 八、真实难点局面怎么处理

下表左列是门店单子上常见的局面，右列是正确反应——**凡是需要业务判断的，都不许在识别阶段替客户决定**：

| 局面 | 正确做法 | 错误做法 |
|---|---|---|
| 单价列整列空着，只有个别行填了数字 | 空着的留空，脚本按留空处理并标注待补 | 把金额列的数字搬到单价列 |
| 一页用圈号分成两三笔 | 记进 note，行与笔分开说明 | 把圈号当数量或整页当一笔 |
| 品名是简写加连笔（如 `14pm改17pm`） | 照抄原文，交给映射表标准化 | 直接写成自己以为的标准型号 |
| 同一张纸上有采购也有销售 | 拆成两行，方向分别填 | 一行混着记，或全按采购入账 |
| 数字被笔迹压住、两位叠在一起 | 候选值 + 补拍 | 挑一个看着顺眼的填上 |
| 单据缺日期或合计 | 缺的留空并标注，不推算 | 用前一笔的日期或合计顶上 |

## 九、认得够用的验收标准

一批单据跑完，同时满足下面四条才算「这张单认得住」：

1. 每行的品名、数量、单价、金额里，**至少三个是高分字段**，第四个能被价格库或单据合计验证；
2. **识别出的行数与 P0 数出来的行数一致**，不多不少，跳号处已点名；
3. 单据写了合计的，`数量×单价` 加总与合计的差异在容差内（默认 0.01，抹零级另标）；
4. 所有低置信与带候选的格子都在补拍清单里，没有一条被静默「修好」。

达不到就补拍重跑——**宁可信一张拍清楚的照片，别信一份看起来完整的错表。**

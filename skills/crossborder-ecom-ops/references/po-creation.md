# 阶段 4：PO 单制作

目标：把选品/补货需求表和供应商报价，转成**供应商可直接执行、财务可直接付款、系统可直接导入**的采购订单，并在此之前把所有能拦下来的错误拦下来。PO 出错直接等于资金损失，因此本阶段的校验比生成更重要。

## 入参

- **需求侧**：选品/补货需求表（SKU、数量、目标仓、期望到仓日、优先级）。
- **供应商侧**：报价表（单价、阶梯价、MOQ、交期、币种、贸易条款 EXW/FOB/CIF/DDP、是否含税、包装要求）。
- **商务侧**：付款条件（如 T/T 30%+70%、账期）、验货方式（自检/第三方）、贴标与包装要求、原产地证与认证要求。
- **约束侧**：本次采购预算上限、审批阈值、汇率与锁汇日期。

## 字段字典

表头（PO header）：`po_no`、`supplier`、`currency`、`trade_term`、`payment_term`、`order_date`、`etd`（预计发货日）、`warehouse`、`total_amount`、`prepared_by`。

明细行（PO line）：`line_no`、`sku`、`product_name`、`spec`（颜色/尺码/规格）、`qty`、`unit`、`unit_price`、`amount`、`moq`、`lead_time_days`、`remark`。

## 校验规则

生成前逐项检查，任何一条不过就进 `flags`：

| 检查 | 触发条件 | 处理 |
|---|---|---|
| 必填缺失 | `sku` / `qty` / `unit_price` 为空或无法转成数字 | 该行隔离，`high`（缺单价不可下单） |
| 数值非法 | `qty <= 0`、`unit_price < 0` | 隔离该行 |
| 重复行 | 同 `sku` + 同 `spec` 出现多行 | 标记并给出合并建议，由人工确认是拆单还是重复 |
| MOQ 不足 | 下单量低于供应商 MOQ | `medium`，给出补足到 MOQ 或放弃的建议 |
| 阶梯价跨档 | 数量落在阶梯分界处 | 提示按哪一档计价，必要时拆单更便宜时给出对比 |
| 单位不一致 | 混用件/箱/托 | `medium`，先统一口径再算金额 |
| 币种不一致 | 报价币种 ≠ 下单币种 | `high`，需汇率来源与日期 |
| 含税口径不明 | 报价未说明含税与否 | `medium`，按不含税保守处理并标注 |
| 金额复核 | 行金额合计 ≠ 表头总额（或与需求表金额不一致） | `high`，先查差异再下单 |
| 审批阈值 | 总额超过 `--max-amount` | `high`，进资金终审 |
| 交期风险 | `etd` 晚于期望到仓日 | `medium`，给出必须提前下单的日期 |
| 新供应商 | 供应商首次合作 | `high`，建议缩短账期或做小批量首单 |

## 输出

1. **PO 单**（CSV，可直接发供应商或导入 ERP）：表头信息 + 明细行 + 合计。
2. **校验报告**（JSON）：通过项、隔离行、`flags`、需要人工确认的问题清单。
3. **待办清单**：谁确认什么、什么时候确认，例如「确认阶梯价档位」「补足 MOQ」「锁定汇率」「审批预算」。

## 常见坑

- 单位混用（箱/件）导致数量差几十倍，是最高频的金额错误来源。
- 报价含税与否没写清，财务付款时才暴露。
- 交期从下单日算还是从付款日算，不同供应商口径不同；`etd` 必须写明依据。
- 阶梯价跨档时，拆分下单可能更便宜（也更快），值得直接对比给用户。
- 汇率用付款日还是下单日，影响实际成本；锁汇信息要进 PO 备注。
- 重复下单：同一 SKU 在多个需求表里都出现，合并前先查已下未到货的 PO。
- 认证与标签要求没写进 PO，货到仓被拒收或平台下架，返工成本远高于采购差价。
